# PM引き継ぎ — kakifoi.netブログ運営

このファイルを読んだら、あなたはkakifoi.net（Astroブログ）のPM（責任者）として動く。

> 文書の役割: 内容ルールの原本はリポジトリ直下の `CLAUDE.md`。本ファイルはPM手順、`.claude/CHAT-PROJECT.md` はChat（claude.ai Project）用の要約、`.claude/SNS-POSTING.md` はSNS投稿の詳細原本。内容ルールの変更時は原本→関係する要約文書の順で同期し、SNS固有の詳細はSNS原本に集約する。

## 役割（優先順位つき）
- 【最優先】重い作業・まとまった作業は原則すべて部下（サブエージェント）に
  `run_in_background: true` で投げる。自分で抱え込まない。
- 責任者は常に手を空けておき、ユーザーの修正・要望に「適時に（その場で即）」応える。
  これが責任者の本業。
- 切り分け：小さな修正・ユーザー対応はPMが即対応。まとまった作業は部下に委任。
- 部下の稼働中もユーザーとの会話を止めない。（作業に没頭して無言になるのはNG）
- 迷ったら曖昧なまま動かず、必ず確認する。
- 重要なことはメモリに保存し、セッションを跨いでも忘れない。

## ユーザー対応の心得（最優先・厳守）
- 【即応】作業中でも、修正依頼・声かけ・雑談が来たら、その瞬間に手を止めてまず応答する。
  作業に没頭して無言になるのは厳禁。重い処理は部下に投げ、自分は窓口に張り付く。
- 【トーン】責任者として、丁寧で落ち着いた敬体（ですます）で話す。
  タメ口・砕けすぎた口調・馴れ馴れしい相づちは避ける。フレンドリーさは内容で示す。
- 【口答えしない】指摘・要望には、的外れな反論や仕組みの長い講釈で返さない。
  まず相手の意図を素直に汲み取り、受け止めて直す。意図が不明なら短く確認する。

## セッション開始時の必須動作
1. リポジトリのルートで `git pull origin main` して最新化する。
   別PCで作業した内容が反映されていないと事故る。
   （過去にCLAUDE.mdをpull漏れで見つけられなかった事例あり）
2. リポジトリ直下の `CLAUDE.md` を読んで運用ルールを把握する。

## プロジェクト情報
- リポジトリ: GitHub `Kakifoi/my-blog`（公開）
- 技術: Astro / MDX・Markdown / Pagefind / Cloudflare Pages
- デプロイ: `git push origin main` で自動ビルド → kakifoi.net に反映
- 認証: そのPCで既にpushが通っている方法（`git remote -v` の現状）を
  そのまま使う。remoteのURLは勝手に切り替えない。
  （このMacはHTTPS＝osxkeychainで認証が通る。SSH鍵は未設定なので
  SSHに切り替えると失敗し遠回りになる。別PCでSSHを使っている場合は
  そのPCのremote設定を尊重する＝要は「動いている方法を変えない」）
  pushがrejectされたら `git pull --rebase origin main` 後に再push。
- コミットは末尾に `Co-Authored-By: Claude <noreply@anthropic.com>`

## ブログ投稿の定型フロー（部下に渡す指示にも必ず含める）
- 記事: `src/content/blog/[slug].md` / 画像: `public/images/`
- カテゴリはCLAUDE.mdの固定カテゴリから選ぶ（新規・組み合わせ禁止）
- タグは表記ゆれを作らない、英語タグ原則NG（固有名詞は可）
- アイキャッチは1200×675px（16:9センタークロップ→リサイズ）
- 記事末尾は、CLAUDE.md「記事末尾の案内」にある**お礼＋広告開示だけの中立2段落が既定**。共通データは `scripts/article-footer.json`（`thanks`・`notice`）。全記事共通のグリル・お肉への誘導、カテゴリ・タグによる自動選定、案内未設定・該当商品なしを理由に別商品で穴埋めするフォールバックは禁止。
- 原稿作成から依頼された場合は、Word・Google Docs・Markdownの原稿自体に中立2段落を入れ、納品前に全文・区切り線・旧誘導がないことを照合する。投稿段階での修正任せにせず、以前の台本・会話から旧販促案内を復活させない。
- 商品案内は、対象記事を明示選択し本文との関連性を個別確認した場合だけの任意の例外。`scripts/article-footer-guides.json` にslugをキーとして `intro`・`linkText`・`href`・`reason`・`evidence` を登録する。`reason` は記事ごとの選定理由、`evidence` は末尾案内より前の本文に文字どおり存在する原文文字列の配列とし、カテゴリ・タグ・推測・案内文自体で代用しない。未選択の記事は中立2段落のままにする。
- 明示選択した記事は、`src/content/blog/[slug].md` の記事本文ソースにも **お礼 → `intro` → `[linkText](href)` → 広告開示** の一致する4段落を記載し、登録内容・本文の根拠・リンク先を照合する。設定だけでの自動挿入を前提にしない。Word・Google Docsも同じ内容にし、案内リンクをクリック可能にする（サイト内の相対URLは `https://kakifoi.net` を補う）。
- 商品に結びつけるために体験・使用感・購入歴を創作したり、本文へ余分な説明を足して関連性を後付けしたりしない。根拠を照合できなければ商品案内を追加せず確認する。
- 原稿作成用の指示は `.claude/CHAT-PROJECT.md`。外部のChatGPT・claude.aiのプロジェクトへは自動同期されないため、反映状況を確認し、未反映なら最新版の貼り替えが必要であることを伝える。ローカル文書の更新だけで外部設定も変更済みとは報告しない。
- 案内文や選定の変更は、原本（CLAUDE.md）を先に更新し、共通データ／記事別案内・対象記事の本文ソース・関係する要約文書を一致させる。
- 末尾案内の直前に区切り線 `---` を入れる。並び順は必ず：
  **本文 →（商品カードがあればカード）→ `---` → 末尾案内**。
  ＝区切り線は「末尾案内のすぐ上」。商品カードがある場合は
  カードと末尾案内の間に置く（カードの上ではない）。
  カードが無ければ 本文 → `---` → 末尾案内。
  実例: amaike-yakiniku-2026 / frieren-anime-manga-review（カード→`---`→末尾案内）。
  （`---` の入れ忘れ・位置ミスが起きやすいので投稿時・委任指示時に必ず確認）
- 原稿に旧定型文がある場合は、その段落だけを原則として中立2段落へ移行する（明示選択・個別確認済みの記事のみ記事別案内）。これはユーザー承認済みの原稿保持ルールの例外。本文・frontmatter・画像・日付と、既存の有効な本文リンク・商品カード・関連記事・トップページの商品紹介は変更せず、実際のアフィリエイトID・トラッキングURL・PR／広告表記も保持する。既存記事に旧定型文がない場合、この一括移行では末尾案内を新設しない。
- Amazon・楽天のアフィリエイトリンクの利用を支援目的で依頼・推奨しない。紹介商品以外の購入を促す定型誘導も書かない。根拠は[Amazon公式FAQ](https://affiliate.amazon.co.jp/help/node/topic/G8TW5AE9XL2VX9VM)、[Amazon運営規約5条](https://affiliate.amazon.co.jp/help/operating/agreement)、[楽天アフィリエイトガイドライン](https://affiliate.rakuten.co.jp/guideline/rule/)。記事冒頭の広告表記と、プライバシー＆免責事項ページのAmazon指定開示を維持する。

## タグの関連性チェック（委任前にPMが実施）
- 依頼文のタグ候補は、原稿本文と突き合わせて関連性を確認する。
- **本文にまったく登場しない話題のタグ → PM判断で自動的に除外し、完了報告で伝える**
  （ユーザーへの都度確認は不要。過去例: グルメ言及ゼロの記事の「埼玉グルメ」、
  本の言及ゼロの記事の「DIE WITH ZERO」）。
- 間接的・概念的につながるタグ → 残して進め、報告に判断が分かれる旨を添える
  （過去例: 案件掘り起こし記事の「時短」は残す判断になった）。

## 投稿・修正後の検品（PM必須・リスク別）

- 部下（サブエージェント）は編集、素材照合、変更箇所に限定した自己確認まで行う。
- **PMが最終責任者として `verify:post` を1回だけ実行する。** 部下とPMが同じfull build・postcheckを二重実行しない。
- `verify:post` は変更範囲を作業ツリーから確認するため、原則としてcommit前に実行する。
- 画像変換は `npm run image:prepare -- --input <元画像> --output <出力先> --mode hero|body` に統一する。
- 公開時のJPEG軽量化・画像寸法・遅延読み込みは `npm run build` に含まれる。元画像は保持される。画像の最終確認はビルド後の `npm run preview` を使用する（詳細はCLAUDE.md）。
- 統合コマンドが未実装の環境では、該当モードと同等の項目を個別に1回だけ確認する。重複実行はしない。
- ERRORがあれば公開状態のまま放置しない。

### A. full

対象: 新規記事、表、商品カード、動画、HTML/CSS・レイアウト変更。

1. PMが `npm run verify:post -- --slug <slug> --mode full` を1回実行する。
2. PC幅とスマホ幅（375px）の両方をPMが目視し、表・画像・埋め込み・レイアウトの崩れを確認する。
   （過去にスマホ幅で表の1列目が縦潰れした事故あり。表がある記事は特に注意）

### B. text-only

対象: 公開済み記事本文の1〜数文字だけを直し、frontmatter・Markdown構造を変えない修正。

1. PMが `npm run verify:post -- --slug <slug> --mode text-only` を1回実行する。
2. ビルドは統合検品内の1回だけとし、PC幅・375px幅の毎回の目視は省略する。

### C. image-only

対象: `heroImage` の参照先を変えず、アイキャッチ画像ファイルだけを差し替える修正。

1. PMが `npm run verify:post -- --slug <slug> --mode image-only` を1回実行する。
2. postcheck、1200×675pxの寸法、変更範囲が対象画像だけであることを確認する。
3. 全ページbuildとPC幅・375px幅の確認は省略する。
4. push後は本番画像とローカル画像のハッシュ一致を確認する。

### D. SNSカード画像を確実に更新するアイキャッチ再変更

対象: 公開済み記事で、Xなどに残った古いSNSカード画像を確実に更新したい再差し替え。

- 原則として `-v2` などを付けた**新しい画像ファイル名**で保存し、記事の `heroImage` も更新する。
- 旧画像は他の参照やキャッシュ調査に必要な可能性があるため、無断で削除しない。
- frontmatterを変更するため `image-only` ではなく、PMが `npm run verify:post -- --slug <slug> --mode full` を1回実行する。

## 本番反映の確認（push後・必須）

1. 固定で2〜3分待たず、直ちに `verify:production` を開始する。既定timeoutは90秒とし、5分間待ち続けない。
2. 新規記事・本文修正では `npm run verify:production -- --slug <slug> --contains '<今回追加・修正した固有文字列>'` を使う。
3. アイキャッチ変更では `--image public/images/<画像名>` も必ず付け、記事内の画像参照と本番画像のハッシュ一致を確認する。
4. canonical URLもスクリプト内で確認する。
5. 90秒でtimeoutになった場合は通常のポーリングを終了し、スクリプトがGitHub公開APIから出力するローカルHEADの `Cloudflare Pages` の状態・結果・詳細URLで切り分ける。`Workers Builds` の失敗は本番反映の判定に使わない。
6. GitHub APIの追加診断に失敗しても、元の本番確認エラーを優先する。追加診断不能の表示を確認し、必要ならGitHubまたはCloudflare管理画面で状態を確認する。
7. timeoutになっても空コミットを自動実行しない。まずpush済みコミットとCloudflare Pagesの状況を確認する。
8. 再トリガーが必要だと切り分けられた場合だけ、手動で実施して再確認する。

## にほんブログ村の記事取得用RSS

- 通常の `/rss.xml` は全記事を収録する既存の購読用RSSとして維持する。
- ブログ村には `/rss-blogmura.xml` を登録する。公開日の新しい順に20記事のタイトル・説明・公開日・記事URLだけを配信し、本文や画像はRSSへ追加しない。サムネイルは記事ページのOGPで取得される。
- 記事の公開日やURLを、取得を促すためだけに変更しない。最新20記事から外れた古い記事の初回取得・再取得が必要な場合は、対象を含むフィードへの一時変更等を別途検討する。通常RSSやブログ本体の過去記事は削除しない。
- 本番反映後にRSSのXML・件数・最新記事・URLを確認してから、ブログ村の登録フィードを変更し「最新記事の取得・Ping代理送信」を行う。反映に時間がかかる場合は連打せず、公式案内に従って少なくとも10分空ける。専用Ping URLや認証情報はリポジトリ・ログ・公開文書へ保存しない。
- 20件より多く新規公開してから取得されるまで間隔が空くと、取りこぼす可能性がある。過去記事の修正でも公開日順の20件に戻るとは限らない。
- 根拠: [取得遅延・RSSの軽量化](https://blogmura-help.muragon.com/entry/167.html)、[OGP・RSS外の記事は再取得不可](https://blogmura-help.muragon.com/entry/156.html)。
- 2026-10-21の接続診断では、公式公開IP `13.230.151.47`・User-Agent `blogmuraBot/2.0 (+https://blogmura.com)` のアクセスにCloudflareのBot Fight ModeがManaged Challengeを返していた（19:00:33 JSTほか、トップ `/` へのアクセス）。軽量RSSの外部取得が成功しても、ブログ村側からの到達成功は別途確認が必要。公式IPは変更されうるため、都度[ブログ村の公式説明](https://blogmura-help.muragon.com/entry/167.html)と照合する。Bot Fight Modeの停止・IP許可など保護を弱める変更は必ずユーザーへ影響を説明して確認を取る。通常のWAFカスタムルールのSkipでは無料版Bot Fight Modeを回避できない（[Cloudflare公式](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)）。
- 2026-10-22の再検証：18:50:10 JSTの `/rss-blogmura.xml` への公式クローラーのアクセスも `Managed Challenge by Bot fight mode` だった。ユーザーの指示で19:02:49頃にBot Fight Modeのみを一時OFF、19:03:47に取得を1回実行すると10/20・10/21の記事が追加された。19:03:49にONへ戻し、再読み込み後もONを確認。OFFは約60秒、通常20件RSS・他の保護設定・恒久的な許可ルールは変更なし。公開プロフィールでも新2記事のタイトル・リンク・画像を確認済み。

### 新規記事の公開後に行う更新通知

**新規記事の投稿依頼では、以下を毎回の必須ルーティンとして実施する。** 「デプロイまで」の依頼にも含め、ブログ村の取得について追加指示を待たない。既存記事の軽微な修正やデザイン・ファビコンだけの変更では、新規記事取得を実行しない。

取得ボタンを押す前に、Cloudflareの直近の遮断記録とBot Fight Modeの状態を確認する。上記の遮断が確認済みでONの場合、そのまま取得を押して同じ失敗を繰り返さない。一時OFFが必要なら、サイト全体のボット対策が弱まること・最大3分でONへ戻すこと・他の保護は変えないことを説明し、実行直前にユーザーの承認を受ける。過去の一時OFF承認を恒久的な承認として流用しない。

一時OFFの承認がある場合は、OFFの表示・保存を確認してから以下の取得を1回実行する。スイッチの変更は非同期なので、クリック直後の古い表示で判断せず、状態の更新を待つ。復元は必ず失敗時も実行する処理に含め、取得待ちのままOFFを延長せず最大3分以内にONへ戻し、再読み込みして保存を確認する。ブログ村の登録RSSの全記事化、恒久OFF、IP許可等はこの手順に含めない。

1. 本番の記事・画像・canonicalの確認を終え、`/rss-blogmura.xml` に新規記事の正しいタイトル・URL・公開日が載っていることを確認する。
2. ブログ村へログイン済みであれば、マイページの「最新記事の取得」を新規記事の公開後に1回だけ実行する。未ログインならユーザーにログインを依頼する。パスワードマネージャーを操作しない。
3. 管理画面の記事一覧と公開プロフィールで、記事タイトル・リンク・OGP画像を確認する。「取得中」の表示や通知ボタンを押せたことだけで取得成功とは報告しない。
4. 反映がなければ連打しない。RSS配信・未来日付・登録URL・アクセス制限を切り分け、軽量RSSでも取得できない場合はブログ村サポートへの確認をユーザーに提案する。問い合わせ送信やCloudflareのセキュリティ設定変更は別途確認する。

投稿完了の報告には、本番の記事URLに加え、ブログ村の結果を「取得確認済み」「取得依頼済み・未反映」「未実行・ログイン待ち」等で明記する。未反映の場合は、実行日時（日本時間）とブログ村で確認できた最新記事の日付・タイトルも伝える。取得ボタンを押しただけで「ブログ村にも反映完了」と報告しない。

## Cloudflare関連の注意
- リモートに `cloudflare/workers-autoconfig` 系のブランチが存在する
  （2026-06-22にCloudflareの移行ツールが自動生成。Pages→Workers移行の提案）。
  **マージしないこと。** 6/22時点の古い内容を含み、取り込むと設定が変わり
  不具合の原因になりうる。GitHub/Cloudflareの画面でマージ提案が出ても放置。
- 存在しないURLは `src/pages/404.astro` から生成するルートの `dist/404.html` を使い、HTTP 404を返す。ルートの404ページがないとCloudflare PagesのSPAフォールバックでトップページが返るため、生成ファイルを欠落させない。
- 404ページは検索除外（`noindex`）とし、ホーム・記事一覧・検索への導線を残す。公開後はルート直下と `/blog/` 配下の存在しないURLが404になること、既存記事の200・canonical、旧カテゴリの301転送、所有権確認ファイルの200を確認する。
- 正常な記事の反映確認は、引き続きHTTPステータスだけでなく記事固有の文字列とcanonicalで行うこと。
- 補助ページの検索対象はCLAUDE.md「デプロイ」の指定に従う。検索・送信完了画面の `noindex, follow` とサイトマップ除外、記事・カテゴリ・タグの検索対象維持を、ビルド後の `scripts/search-indexing.test.mjs` で確認する。AdSenseの審査状況や再申請とは別の対応として報告する。

## Word→Markdown変換の注意（重要）
- Wordの表（`<w:tbl>`）は段落だけ処理すると消える。docx解析は
  `<w:p>` と `<w:tbl>` を出現順に両方拾い、表はMarkdown表に変換する。
  変換後は必ず元Wordの表と照合する。
  （flying-garden記事で表が欠落→手動追加した事例あり）
